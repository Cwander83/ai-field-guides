02 • Architecture Selection Choosing Between Inline, Subagents, Forks & Peer Swarms

Four Multi-Agent Topologies & When to Delegate

"Multi-agent coding" actually describes four distinct operating patterns. Picking the right pattern before you write a prompt saves both wall-clock time and 3x–5x in wasted token spend.

1 Single Agent (Inline Default)

One context window, one tool loop. Best for 30-second targeted edits, interactive steering, and sequential steps that all rely on the exact same files already in memory.

2 Focused Subagent (Hub-and-Spoke)

Coordinator spawns clean-slate specialists (researcher, test-writer, reviewer) via sequential pipelines, parallel fan-out, or intent routing, then merges their summaries.

3 Context Fork (/subtask • fork)

Clones your entire active conversation into a background branch sharing your prompt cache. Ideal when a side task needs everything discussed so far without polluting your main thread.

4 Peer Swarm / Agent Team

Multiple long-lived peer sessions collaborating across a shared message board or task roster (Antigravity /teamwork Swarms, Claude Agent Teams) on multi-hour parallel builds.

What Subagents Are NOT: 4 Myths That Burn Budgets
1. Not automatic edit safety: Two workers editing the same file concurrently will overwrite each other unless you partition folders or enable isolation: worktree. • 2. Not a free cache: Every fresh spawn re-reads files unless you resume its Agent ID. • 3. Not zero-cost: Five parallel agents spend ~5x the tokens. • 4. Not a replacement for Skills: If a reusable workflow needs main-chat context (like formatting a commit), make it a SKILL.md, not a subagent.

04 • Configuration Reference Visual Topologies & Complete YAML Frontmatter Schema

The 4 Topologies & Subagent Frontmatter Reference

A subagent file is plain Markdown: YAML frontmatter between --- fences on top, and the specialist's system prompt below. Only name and description are mandatory—every other key sharpens cost, isolation, or safety.

1. SINGLE AGENT: One shared context & tool loop.
2. HUB & SPOKE: Coordinator dispatches scoped workers.
3. CONTEXT FORK: Splits live thread w/ shared cache.
4. PEER SWARM: Lateral mesh on shared task board.

Complete Subagent YAML Frontmatter Reference

Field Req? Behavior, Precedence & Practical Guidance
name Yes Unique lowercase-hyphen ID (e.g., codebase-researcher). Avoid colons (reserved for plugin namespaces).
description Yes Natural-language classifier trigger telling the coordinator when to delegate (all agents share a 15K-token startup budget).
tools No Explicit allowlist (Read, Grep, Glob, Bash). Warning: omitting tools inherits every session & MCP tool!
disallowedTools No Denylist subtracted before tools resolves (e.g., Write, Edit, Agent, mcp__github).
model No haiku, sonnet, opus, full ID, or inherit. Precedence: per-call → frontmatter → CLAUDE_CODE_SUBAGENT_MODEL → parent.
permissionMode No default, acceptEdits, auto, dontAsk (pre-allowed only), plan (read-only), or bypassPermissions (CI containers only).
hooks No Agent-scoped lifecycle scripts (PreToolUse, PostToolUse, Stop) to validate CLI arguments or auto-format edits.
isolation • maxTurns • memory No isolation: worktree prevents parallel edit collisions; maxTurns caps runaway spend; memory: project persists notes.
Pre-Flight Validation Tip: Catch YAML Typos Before Starting a Session
Broken YAML or missing name / description keys cause silent skips at startup. Run claude plugin validate .claude/agents (and /doctor to spot duplicate names) right after editing!

06 • Runtime Mechanics Invocation Modes, Context Forks, Resuming & Nesting Limits

Invocation Mechanics, Context Forks & Concurrency

Understanding what crosses the context boundary at launch—and when to reach for a fork or resume instead of a fresh spawn—eliminates the "amnesia tax" between pipeline stages.

Four Ways to Trigger a Subagent (From Soft Routing to Guaranteed Pinning)

Trigger Mechanism Syntax Example Guarantee & Under-the-Hood Behavior
1. Automatic Delegation "Audit the auth module and summarize risks." Coordinator matches task intent against loaded description strings and calls the Agent tool automatically.
2. Natural-Language Name "Use the skeptical-reviewer agent on my diff." Very high likelihood; coordinator still composes the task briefing passed across the boundary.
3. Explicit @ Mention @agent-skeptical-reviewer check HEAD~1 Guaranteed execution of that exact subagent. Note: your coordinator still writes the subagent's briefing prompt!
4. Whole-Session Mode claude --agent skeptical-reviewer Runs your main thread itself under that agent's system prompt, tool allowlist, and model from turn one.

Clean-Slate Subagent vs. Context Fork (/subtask • fork)

A Clean-Slate Subagent (Default)
  • Sees at startup: Its own Markdown prompt, the coordinator's briefing, repo CLAUDE.md / AGENTS.md, git status snapshot, and preloaded skills.
  • Watch out: Built-in lightweight scouts (like Explore) skip CLAUDE.md to save tokens—restate critical folder exclusions directly in your prompt!
B Context Fork (/subtask or fork)
  • Sees at startup: Your complete parent conversation history, tools, and system prompt—while keeping all new tool calls isolated in the background!
  • Cache superpower: Shares the parent's prompt cache, making its first turn dramatically cheaper than re-briefing 40K tokens of context from scratch.

Three Runtime Rules Every Orchestrator Should Know

1 Resume, Don't Respawn

Completed agents retain an Agent ID. Asking the coordinator to "resume that same reviewer" sends a follow-up via SendMessage with full history intact—zero re-reading!

2 Nesting Depth Cap (3)

Subagents can spawn child helpers up to 3 layers deep by default (tuned via ..._MAX_SUBAGENT_SPAWN_DEPTH; set 1 for flat hub-and-spoke). Forks never re-fork.

3 Concurrency Ceiling (20)

Up to 20 background subagents run simultaneously before queueing (tuned via ..._MAX_CONCURRENT_SUBAGENTS). Press Ctrl+B anytime to background a live run.

07 • Defense in Depth Least-Privilege Tool Scoping, Permission Modes & Command Hooks

Least-Privilege Scoping & Command-Inspecting Hooks

Once subagents run unattended in the background—often reading untrusted web pages, GitHub issues, or third-party READMEs—prompt politeness is not a security boundary. Enforce blast-radius limits in configuration.

LAYER 1 • TOOLS: Strip Write, Edit & Agent
LAYER 2 • MODE: Use plan or dontAsk
LAYER 3 • HOOKS: Validate exact CLI args

Layer 1 & 2: Tool Filtering Dials & Per-Agent Permission Modes

Allowlist vs. Denylist + Spawn Locking
  • Narrow job? Use tools: tools: Read, Grep, Glob guarantees zero file writes and zero shell access.
  • Broad job? Use disallowedTools: Subtract dangerous capabilities like Write, Edit, mcp__github.
  • Restrict who spawns whom: A main coordinator with tools: Agent(researcher, test-writer), Read is structurally blocked from spawning any unlisted editor!
Choosing permissionMode Safely
  • plan: Enforces structural read-only mode inside scouts.
  • acceptEdits: Smooth local coding inside isolated worktrees.
  • dontAsk: Auto-denies anything outside pre-approved rules—ideal for unattended background runs.
  • Note: If your parent session runs bypassPermissions, children inherit it—reserve bypass strictly for disposable containers!

Layer 3: Argument-Level Guardrails with a PreToolUse Bash Hook

Giving an analyst tools: Bash lets it run psql—but also rm -rf! Pair frontmatter hooks with a 10-line validator script where exit 2 blocks bad commands and feeds stderr straight back to the subagent: 

# .claude/agents/db-analyst.md
---
name: db-analyst
description: Read-only SQL reporting analyst.
tools: Bash, Read
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/readonly-sql.sh"
---
#!/usr/bin/env bash
# ./scripts/readonly-sql.sh (remember: chmod +x!)
CMD=$(jq -r '.tool_input.command // empty')
if echo "$CMD" | grep -qiE \
  '\b(INSERT|UPDATE|DELETE|DROP|ALTER|TRUNCATE|rm)\b'; then
  echo "Blocked: SELECT queries only." >&2
  exit 2   # Hard-blocks call & informs agent!
fi
exit 0

10 • Production Pipeline & Economics End-to-End Multi-Agent Feature Pipeline & Token Budget Engineering

End-to-End Orchestration Pipeline & Cost Engineering

Smart orchestration pairs a frontier reasoning coordinator with fast, inexpensive specialist workers—delivering cleaner architecture and independent verification at a fraction of an all-frontier swarm bill.

6 Token & Cost Guardrails That Prevent Multi-Agent Bill Shock

1 Tier Models by Judgment Needed

Keep opus / gemini-pro on your coordinator, pin haiku / flash on file scouts, and use sonnet on builders. Set CLAUDE_CODE_SUBAGENT_MODEL as a safe floor.

2 Cap Fan-Out Width at 3–5 Workers

Five parallel subagents spend ~5x tokens, and ten verbose return summaries will overflow your coordinator's context window! Never fan out what one Grep can answer.

3 Guard the 15K Description Budget

Every installed agent's description loads into session preamble on turn 1. Keep descriptions to 1–2 crisp sentences; put detailed instructions in the Markdown body.

4 Set maxTurns & Round Caps

Put maxTurns: 20–30 on exploratory or review agents, and cap critic loops at 3 rounds where only blocking defects trigger another iteration.

5 Use Forks & cacheTtl: 1h

Use /subtask forks when side tasks need heavy shared history (free prompt-cache hit!), and set experimental: { cacheTtl: 1h } on long-running specialists.

6 Enforce Terse Output Contracts

Every token a subagent returns gets billed again on every subsequent turn of your main session. Demand 250-word bulleted memos citing file:line.
