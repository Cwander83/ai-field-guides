A Why DuckDB Wins for AI Agents

Color-Coded Anatomy of a Zero-Ambiguity Metric Spec

1. Metric & Formula → 2. Canonical Grain & Source → 3. Approved Join Paths → 4. Mandatory Exclusions → 5. Guardrail Bounds 
metrics:
  - name: net_revenue_usd                          # [1] Exact business name + formula
    formula: "SUM(gross_amount_usd - refund_amount_usd)"
    grain: "1 row per order_id in analytics.v_orders_masked (UTC)"   # [2] Base grain
    joins:                                           # [3] Pre-approved join keys only
      - "LEFT JOIN analytics.dim_accounts USING (account_id) -- many-to-one"
    default_filters:                                 # [4] Always-on hygiene rules
      - "order_status = 'settled' AND is_internal_test = FALSE"
    validation_bounds:                               # [5] Catch silent data bugs
      - "refund_rate_pct BETWEEN 0 AND 25; net_revenue_usd >= 0"

Automated Verification, Charting & Narrative Exports

The most dangerous failure mode in AI analytics isn't a syntax error—it's a confident executive summary where the LLM mis-sums a 12-row table or plots unverified outliers. Enforce the SQL-First Math Rule and bind charts directly to SQL JSON output.

Deterministic Verification: Every chart and KPI callout passes through automated SQL checksums before rendering to stakeholders.
! The SQL-First Math Rule

Never let an LLM perform arithmetic in prose. If your narrative needs a grand total, YoY growth %, 7-day moving average, or rank order, compute it inside the DuckDB query using CTEs, ROLLUP, or window functions: 

WITH monthly AS (
  SELECT DATE_TRUNC('month', order_date) AS mo,
         SUM(net_revenue) AS rev
  FROM v_orders_masked GROUP BY 1
)
SELECT mo, ROUND(rev, 2) AS rev,
  ROUND(100.0 * (rev - LAG(rev) OVER (ORDER BY mo))
        / NULLIF(LAG(rev) OVER (ORDER BY mo), 0), 1) AS mom_pct
FROM monthly ORDER BY mo;
✓ 4-Point Automated Reconciliation
  • 1. Grand Total Tie-Out: Compare SUM(group_rev) against an ungrouped SELECT SUM(net_revenue) to catch dropped NULL categories or fan-out joins.
  • 2. Null & Duplicate Audit: Assert COUNT(*) = COUNT(DISTINCT order_id) on fact tables before aggregating.
  • 3. Period Completeness: Check MAX(order_date) so an incomplete current month isn't plotted as a cliff drop.
  • 4. Unit & Currency Lock: Label columns explicitly (_usd, _pct, _utc) so prose never confuses cents with dollars.

Recipe 1 • S3 Parquet Cohort Retention SQL

WITH cohorts AS (
  SELECT account_id,
    DATE_TRUNC('month', MIN(event_ts)) AS cohort_mo
  FROM read_parquet('s3://lake/billing/*.parquet')
  WHERE status = 'paid' GROUP BY 1
),
activity AS (
  SELECT DISTINCT b.account_id, c.cohort_mo,
    DATE_DIFF('month', c.cohort_mo,
      DATE_TRUNC('month', b.event_ts)) AS mo_num
  FROM read_parquet('s3://lake/billing/*.parquet') b
  JOIN cohorts c USING (account_id)
)
SELECT cohort_mo, mo_num, COUNT(*) AS active_accts
FROM activity GROUP BY ALL ORDER BY 1, 2 LIMIT 200;

Recipe 4 • Safe Python SQL Guardrail Wrapper

import duckdb, sqlglot

def run_safe_sql(con, sql: str, max_rows: int = 500):
    parsed = sqlglot.parse_one(sql, read="duckdb")
    if parsed.key not in ("select", "union"):
        raise ValueError("Blocked: SELECT-only policy")
    con.execute(f"EXPLAIN {sql}")  # Validate plan first
    wrapped = f"SELECT * FROM ({sql.rstrip(';')}) LIMIT {max_rows}"
    return con.execute(wrapped).fetchdf()

con = duckdb.connect("warehouse.duckdb", read_only=True)
con.execute("SET memory_limit='2GB'; SET threads=4;")

Security, PII Masking & Cost Guardrails

Giving an LLM direct database access without defense-in-depth risks leaked customer PII, runaway cloud bills, or indirect prompt injection hidden inside user-submitted text fields (like support tickets or company names). Enforce all five layers below at the database and harness level—never rely on system prompts alone.

Guardrail Layer Threat Mitigated Concrete DuckDB / MotherDuck Implementation
1. Engine Read-Only Accidental DROP, DELETE, UPDATE, or COPY TO exfiltration Connect with read_only=True, --read-only flag, or MotherDuck remote MCP restricted to query (disable query_rw).
2. Masked Views Only PII leakage (emails, phones, SSNs, API keys) into LLM context Grant agent access solely to v_*_masked views using SHA256 hashes and SELECT * EXCLUDE (email, ssn).
3. External Access Lock SSRF or reading arbitrary local files via read_text('/etc/passwd') Set SET enable_external_access = false; after attaching approved catalogs/tables so agents cannot probe the host filesystem or HTTP.
4. Resource & Row Caps OOM crashes, runaway S3 scans, or 500K-token context floods Enforce SET memory_limit='2GB';, SET threads=4;, query timeout (15–30s), and wrapper LIMIT 500 on every query.
5. Data-Row Sanitization Indirect prompt injection inside free-text columns Strip or truncate raw free-text fields in analytical views; treat all returned SQL cell values as untrusted data, never instructions.

PII-Safe Analytical View Template

CREATE OR REPLACE VIEW analytics.v_orders_masked AS
SELECT
  order_id,
  SHA256(LOWER(TRIM(customer_email)) || 'salt_2026')
    AS customer_hash,
  REGEXP_REPLACE(customer_email, '^[^@]+', '***')
    AS email_domain_only,
  plan_tier,
  gross_amount_usd,
  refund_amount_usd,
  order_date,
  is_internal_test
FROM raw.orders
-- Excludes raw email, card_last4, phone, and free-text notes;

Troubleshooting Clinic (Top 7 Fixes) & Pre-Flight Checklist

When an AI SQL agent returns surprising numbers, slow scans, or empty tables, diagnose the root cause in seconds using the seven fixes below—then run the 6-point checklist before deploying any agent to teammates.

Symptom Root Cause Exact Fix
1. Inflated Revenue Totals Agent joined 1-to-many tables (e.g., orders → line items) causing fan-out double counting Document join cardinality in metrics.yaml and pre-aggregate child tables in a CTE before joining.
2. Zero Rows Returned Case/enum mismatch (e.g., 'Active' vs 'active' or 'US' vs 'USA') Instruct agent to run SELECT DISTINCT col LIMIT 25 whenever a filtered query returns 0 rows.
3. Out-of-Memory (OOM) Crash Unbounded wide join or sorting 50M rows without spill-to-disk config Set SET memory_limit='4GB'; SET temp_directory='/tmp/duck'; and prune columns before joining.
4. Agent Sums Differ from SQL LLM mentally summed table rows in prose instead of reading a SQL total row Enforce SQL-First Math: compute totals/YoY% via GROUP BY ROLLUP or window functions in SQL.
5. Slow S3 Parquet Scans Missing Hive partition filter or scanning uncompressed CSVs repeatedly Enable hive_partitioning=true, filter on partition keys, and convert hot CSVs to ZSTD Parquet.
6. Date / Timezone Drift Mixing local timestamps with UTC dates shifts late-night orders across months Normalize all timestamps to UTC inside canonical views (AT TIME ZONE 'UTC') and note UTC in YAML.
7. Context Window Overflow Agent ran SELECT * without a row cap and dumped 10,000 rows into chat Enforce --max-rows 500 in MCP server args and wrap queries with an automatic LIMIT 500.

6-Point Production Pre-Flight Checklist

✓
Read-Only Enforced at Engine Layer: Verified --read-only / ACCESS_MODE='READ_ONLY' (and MotherDuck query_rw disabled) so writes fail hard.
✓
PII-Masked Views Only: Raw emails, phones, tokens, and free-text notes are excluded or SHA256-hashed before the agent ever sees a schema.
✓
5-Part metrics.yaml Loaded: Core KPIs (revenue, churn, retention) define formula, grain, join paths, exclusions, and sanity bounds in Git.
✓
EXPLAIN + LIMIT + Timeout Active: Every agent query passes AST/EXPLAIN validation, caps rows at ≤500, and aborts after 15–30s.
✓
SQL-First Math & Tie-Out: Totals, averages, and period deltas are computed inside DuckDB SQL and reconciled against an ungrouped grand total.
✓
Auditable Citations Required: Every chart or executive narrative prints the exact SQL query, row count, date window, and semantic spec version.
