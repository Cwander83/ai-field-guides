Prerequisites, Flag Migration & Strategy Matrix

Before flipping cacheComponents: true, verify that your project runs Next.js 16.3+ App Router and strip out legacy route-segment flags that conflict with fine-grained prerendering.

1 Upgrade to Next.js 16.3+ & Check App Tree
# Upgrade Next.js, React, and codemods together
npx @next/codemod@latest upgrade latest
npx next --version   # Must be 16.3.0 or newer

Cache Components applies to app/ (or src/app/). If both folders exist, Next.js builds app/ and silently ignores src/app/. Hybrid pages/ routes continue working untouched.

! Remove Fatal & Legacy Config Keys
  • experimental.dynamicIO is fatal: Renamed to top-level cacheComponents; leaving the old key aborts startup before any build runs.
  • Remove experimental.useCache: Deprecated alias once cacheComponents: true is enabled.
  • Inventory route exports: cacheComponents: true errors on any file still exporting dynamic, revalidate, or fetchCache—migrate those manually first (existing fetch & unstable_cache calls can stay).
// next.config.ts — clean Next.js 16.3+ baseline (delete experimental.dynamicIO first!)
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}
export default nextConfig

The codemod adds export const instant = false to every segment intentionally. During next build, the highest ancestor instant = false shields its entire subtree; during client-side navigations, Next.js still validates each descendant segment individually. Removing opt-outs top-down keeps every child safely deferred until you reach it.

04 • Resolving Blocking Prerenders Request-Time Reads, Sync-IO & Client Hook Blockers

Resolving the 3 Blocker Classes

Almost every prerender error during Cache Components adoption belongs to one of three predictable families. Fix the exact offending boundary rather than wrapping whole pages in a giant fallback.

1 Request-Time Reads

Culprits: cookies(), headers(), await params, await searchParams at page or layout top.

Fix: Move the read into a focused child component inside <Suspense>. Never await params at page top—forward the params or searchParams promise straight into the child and await it there.

2 Sync-IO Calls

Culprits: new Date(), Date.now(), Math.random(), crypto.randomUUID() during render.

Fix: These fail next build even with instant = false! If inside a shared layout, they break every child route. Run --debug-prerender, move into a "use cache" helper, or isolate behind <Suspense> / connection().

3 Client Nav Hooks

Culprit: blocking-prerender-client-hook from usePathname() or useSearchParams() in root nav.

Trap: Static pages pass (pathname is known at build) and hide the bug until you hit a dynamic route! Wrap the hook-reading client leaf in <Suspense> while keeping the outer nav bar static.

// WRONG: top-level await blocks the entire route shell
export default async function PostPage({
  params,
}: { params: Promise<{ slug: string }> }) {
  const { slug } = await params // Blocks before Suspense!
  return <Article slug={slug} />
}
// RIGHT: forward the promise into a Suspense child
export default function PostPage({
  params,
}: { params: Promise<{ slug: string }> }) {
  return (
    <ShellLayout>
      <Suspense fallback={<ArticleSkeleton />}>
        <ArticleBody params={params} />
      </Suspense>
    </ShellLayout>
  )
}
Solid Shell, Suspended Holes: Your outer layout and cached components form a rigid emerald glass frame that renders on frame 1, while live request-time reads (cookies(), headers(), forwarded params, and usePathname() leaves) stream cleanly into recessed <Suspense> bays.

05 • Deterministic Caching & Boundary Anatomy Mastering "use cache", cacheLife, Keys & Revalidation

Mastering "use cache", cacheLife & Keys

When data is shared across visitors or changes on a predictable schedule, promote it into your static shell with "use cache" instead of streaming it on every request.

Data-Level vs. UI-Level Cache + Revalidation

import { cacheLife, cacheTag, updateTag } from 'next/cache'

export async function CatalogGrid({ category }: { category: string }) {
  'use cache'
  cacheLife('hours')              // Built-in or custom profile
  cacheTag('catalog', 'cat-' + category)

  const items = await db.products.findMany({ where: { category } })
  return <ProductCards items={items} />
}

// Inside a Server Action after mutation:
export async function publishProduct(category: string) {
  'use server'
  await db.products.create(...)
  updateTag('cat-' + category)    // Immediate read-your-own-writes
}

Cache Key Rules & Request-Data Guardrails

1 Automatic Key Hashing: Next.js hashes build ID, function location, serialized arguments, and closed-over values into the cache key.
2 Never Call cookies() Inside "use cache": Read session or locale outside in a <Suspense> parent, then pass serializable primitives (e.g., orgId) in as arguments.
3 Keep CLS Zero: Match <Suspense fallback> dimensions (fixed heights, aspect boxes) to resolved content so streamed inserts never jump the page.

Anatomy of a Clean Cache + Suspense Boundary Refactor

[1. Instant Static Chrome] [2. "use cache" Data/UI Slice] [3. cacheLife + cacheTag] [4. Tight <Suspense> + CLS Fallback] [5. Server Action updateTag]
Render header, sidebar, and page title synchronously outside any boundary so frame 1 paints rich UI. Extract shared catalog or team metadata into an async helper or Server Component marked "use cache" with serializable props. Declare cacheLife('hours') and granular cacheTag('team-' + teamId) so prerender includes the cached slice. Wrap only the personalized user banner or live billing meter in <Suspense fallback={<BannerSkeleton h="48px" />}> passing userId outside the cache. Call updateTag('team-' + teamId) in the mutating Server Action and test the round-trip under next start.
Critical Runtime Trap: Passing next build Does Not Prove "use cache" Is Safe
A hidden cookies(), headers(), or auth session helper called deep inside a "use cache" call tree often passes next build silently, then throws a runtime error when a real user hits next start. Always verify every newly cached subtree against a live production run (next build && next start) and test its mutation invalidation path.

06 • Incremental Top-Down Adoption Loop Un-Opting Feature by Feature & next-dev-loop Verification

Top-Down Loop & next-dev-loop Verification

Adopt one product feature at a time (e.g., app/settings/profile/**), walking strictly top-down from root layout to leaf pages while cross-checking /_next/mcp against a real browser.

1 Why Root Layouts Must Un-Opt First

Validation follows first-explicit-config-wins top-down resolution:

  • Ancestor shields children: Removing export const instant = false on a leaf does nothing while its parent layout still exports instant = false.
  • Children shield ancestor: Removing a layout’s opt-out leaves next build green while child pages keep theirs—actual layout blockers only fire once descendant opt-outs come off!
  • Clean root first: Un-opt app/layout.tsx, clear any Sync-IO or client-hook nav blockers, then descend feature by feature.
2 Scoped Build & Prerender Flags

By default next build exits on the first blocking route. Use these two diagnostic flags when isolating tricky errors:

# Report ALL blocking routes + full file:line traces
npx next build --debug-prerender

# Build ONLY specific file-path globs (NOT URL paths!)
npx next build --debug-prerender --debug-build-paths="app/admin/**/page.tsx"

Passing a URL like /admin matches zero files and silently builds nothing.

Two-View Verification with Turbopack next-dev-loop

# 1. Start Turbopack dev server (default in Next.js 16.3+; avoid --webpack) & bind worktree browser session
SESSION="$(agent-browser session id --scope worktree --prefix next-dev-loop)"
agent-browser --session "$SESSION" --restore --enable react-devtools open http://localhost:3000/settings/profile

# 2. Cross-check framework state over /_next/mcp (SSE responses: extract JSON from data: lines)
#    • get_compilation_issues  → confirms Turbopack compile is clean
#    • get_routes              → lists app/ route inventory

#    • get_errors / get_logs   → catches runtime, hydration, and blocking-prerender errors
Check Non-Blank Paint

Verify in agent-browser that frame 1 renders real navigation, headings, and skeletons—not a blank screen.

Check Sibling Routes

Whenever you refactor a shared layout or sidebar component, re-check sibling routes under that layout.

Grow Shells Deliberately

Once green, apply next-cache-components-optimizer to lift shared blocks out of <Suspense> into "use cache".

Per-Route Success Bar: Dev Overlay Clean + Browser Verified + Passing next build
Never delete .next while next dev is running (it breaks active incremental state). When a feature passes next-dev-loop, finish with npx next build as your final commit gate before moving to the next feature.

07 • Partial Prefetching Rollout Shared App Shells, Link Audits & instant-shell-url-data Sweeps

Partial Prefetching (partialPrefetching: true)

Legacy Next.js prefetched entire routes per URL. With partialPrefetching: true, default links reuse one shared App Shell across every dynamic parameter, while only opted-in <Link prefetch={true}> links pre-warm cached URL-specific data ahead of entry.

1 5-Step Staged Rollout Sequence
  1. Audit before enabling: Search app/ and shared components (rg -n '\bprefetch\b|router\.prefetch') for effective prefetch={true} links and imperative router.prefetch() calls.
  2. Lock legacy baseline: Write and pass @next/playwright instant() tests under next start with the flag still OFF.
  3. Stage destinations: Add export const prefetch = 'partial' to audited routes until every locked test passes again.
  4. Flip flag + codemod: Set partialPrefetching: true in next.config.ts and run npx @next/codemod@canary remove-partial-prefetch ./app.
  5. Sweep Insights: Visit routes in next dev to clear any remaining instant-shell-url-data warnings.
// next.config.ts (after Cache Components is green)
export default {
  cacheComponents: true,
  partialPrefetching: true,
}

# Strip temporary route exports cleanly after flag flip:
npx @next/codemod@canary remove-partial-prefetch ./app
Catching instant-shell-url-data Insights
Often fires on generateStaticParams routes where params is already inside <Suspense>, but awaited too high above the URL-specific leaf—tying the shared App Shell to a single URL. Push the await params down into its own leaf boundary.
One Shared Hull, Selective Pre-Warming: Default <Link> navigations share a single cached emerald App Shell across infinite dynamic URLs, while explicit <Link prefetch={true}> paths pre-warm golden-green URL-specific data crystals before the click.

09 • Automated Production Regression Locks @next/playwright instant(), Production Rigs & RED-to-GREEN Contracts

Regression Proof with @next/playwright instant()

Timers are flaky and next dev does not prefetch. Guard your instant navigations with instant() from @next/playwright—a deterministic dynamic-data lock running against a real production build.

1 Expose Testing API in Test Rigs Only
// next.config.ts (gated to E2E/CI test builds)
export default {
  cacheComponents: true,
  partialPrefetching: true,
  experimental: {
    exposeTestingApiInProductionBuild:
      process.env.PLAYWRIGHT_TEST === '1',
  },
}

Run tests against next build && next start. Keep @next/playwright on the exact same release version as next.

2 The Present & Instant + Non-Blank Contract
  • Under the lock (instant()): Dynamic data streams are paused. Your meaningful shell marker MUST be visible (toBeVisible()), and deferred dynamic data MUST still be absent (toHaveCount(0)) to prevent vacuous passes!
  • After lock release: Dynamic content streams in (toBeVisible()).
  • RED → GREEN differential: Prove the test fails RED before your fix, turns GREEN after, and stays non-blank visually.

Production Tests: Soft Client Navigation vs. Hard Initial Load

A. Soft Client Navigation (<Link> Click)

import { test, expect } from '@playwright/test'
import { instant } from '@next/playwright'

test('dashboard soft nav is instant', async ({ page }) => {
  await page.goto('/projects')
  const link = page.getByTestId('nav-analytics-link')
  await expect(link).toBeVisible()

  await instant(page, async () => {
    await link.click()
    await expect(page.getByTestId('analytics-shell')).toBeVisible()
    await expect(page.getByTestId('live-metrics')).toHaveCount(0)
  })
  await expect(page.getByTestId('live-metrics')).toBeVisible()
})

B. Hard Initial Load (page.goto + storageState)

// Inject session via storageState — NEVER call page.goto()
// to log in before instant(), or auth runs unmeasured!
test('analytics hard load serves shell', async ({ page }) => {
  const url = 'http://127.0.0.1:3000/analytics'
  await instant(
    page,
    async () => {
      await page.goto(url)
      await expect(page.getByTestId('analytics-shell')).toBeVisible()
      await expect(page.getByTestId('live-metrics')).toHaveCount(0)
    },
    { baseURL: new URL(url).origin }
  )
  await expect(page.getByTestId('live-metrics')).toBeVisible()
})
Always Assert Both Halves of the Self-Validating Lock
If exposeTestingApiInProductionBuild was accidentally omitted, instant() silently becomes a no-op and a shell-only assertion passes falsely! Checking toHaveCount(0) on a known dynamic node inside the lock guarantees the lock actually engaged.

11 • Diagnostics & Production Launch Readiness Troubleshooting Clinic & 6-Point Pre-Flight Checklist

Troubleshooting Clinic & Pre-Flight Checklist

Most Cache Components and Partial Prefetching snags trace to one of seven concrete patterns. Match your error below for the ten-second fix, then verify your app against the pre-flight checklist.

Symptom / Error Root Cause 10-Second Fix
1. experimental.dynamicIO aborts startup Legacy experimental flag was replaced by top-level cacheComponents in Next.js 16.3+. Delete experimental.dynamicIO (and deprecated experimental.useCache) from next.config.* and set top-level cacheComponents: true.
2. Top-level await params blocks shared shell Awaiting params or searchParams before <Suspense> ties the shell to one URL or fails prerender. Remove await from the page/layout function; forward the params promise into a <Suspense> child and await it inside that child.
3. Sync-IO breaks an instant = false route new Date(), Date.now(), Math.random(), or crypto.randomUUID() ignores opt-outs. Run next build --debug-prerender --debug-build-paths="..." to locate the call; move into "use cache", behind <Suspense>, or use connection().
4. cookies() throws inside use cache under next start next build passed, but a cached helper called cookies(), headers(), or auth session at runtime. Read session/cookies outside "use cache" inside a <Suspense> parent, and pass serializable primitives (like tenantId) as arguments.
5. Only async functions allowed with "use cache" + instant A file with top-level "use cache" also exported const instant = false or read request data. Remove file-level "use cache" from the route file; place "use cache" strictly on pure async data/UI functions inside helper modules or components.
6. Codemod reports 0 ok or misses client-hook error Codemod targeted wrong dir (./app vs ./src/app), or a shared nav calls usePathname(). Re-run codemod against the real app folder (check count > 0), and wrap usePathname()/useSearchParams() client leaves in <Suspense>.
7. <Link prefetch={true}> returns shell-only Destination lacks export const prefetch = 'partial' (or partialPrefetching: true), or URL data isn’t cached. Add export const prefetch = 'partial' during rollout (or enable partialPrefetching: true), wrap URL reads in "use cache", and test under next start.
